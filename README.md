# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

1. 재현할 커밋을 지정해 저장소를 새 폴더에 받습니다. 현재 커밋 전 작전실 변경은 기준 커밋만 받으면 포함되지 않으므로, 이후 저장점에서 실제 포함 커밋을 확인해야 합니다.
2. Node.js 22 이상과 npm, Git을 준비한 뒤 저장소 루트에서 아래 명령을 실행합니다.

```powershell
node --version
npm install
```

3. 서버 설정 이름은 SUPABASE_URL, SUPABASE_SECRET_KEY입니다. 지정 메모 복원을 사용할 때는 RESTORE_NOTE_BACKUP_JSON과 RESTORE_NOTE_CONTENT_SHA256도 필요합니다. 실제 값은 승인된 서버의 비밀 설정 화면에서 직접 입력합니다. Vercel의 배포 커밋 정보는 플랫폼이 제공합니다.
4. 기존 학습 DB의 인증·메모·소유권·승인 테이블 및 서버 전용 RPC 준비 상태를 확인합니다. 승인 절차는 [docs/DEVICE_APPROVAL.md](docs/DEVICE_APPROVAL.md)를 따르며 이미 적용한 초기 SQL을 다시 실행하지 않습니다.

비밀번호·토큰·서버 전용 키·기기 개인키·개인정보·메모 제목/본문은 README, Git, 로그, 제출 JSON이나 배포 패키지에 넣지 않습니다. .env*, artifacts/, bundle-notes.json은 제외 대상입니다. 폴더 전체를 압축하는 대신 제출 대상 파일을 확인합니다.

### 재현 순서 2 — 학생 판정기·탐지 규칙 실행

```powershell
npm run decider:test
npm run fixture:7
npm run detect:test
```

판정 정상 기준은 등록 기기의 허용 구역 요청과 유효 재확인 요청의 allow입니다. 미등록 기기는 deny, 추가 확인 전 복합 이상은 step_up이어야 합니다. 탐지 정상 기준은 10분 120건까지 observe, 초과하면 propose_revocation입니다. 위 명령의 입력은 가상 요청·사건이며 실제 집행 결과는 별도로 기록합니다. 각 명령은 끝나면 종료됩니다.

### 재현 순서 3 — 접속 앱·자료실·작전실 실행

1. 배포할 커밋과 서버 설정을 확인합니다. vercel.json의 빌드 명령은 npm run build, 공개 폴더는 public, 서버 함수는 api/입니다. 로컬 빌드는 `npm run build -- --local`로 확인합니다. 일반 빌드는 Vercel이 제공하는 출처 정보를 요구합니다.
2. 배포 후 /aleph.json의 커밋·단계를 기록하고 실제 저장소와 대조합니다. 기존 judgeIssuer와 신원 발급자 계약을 유지합니다.
3. 자료실 첫 화면에서 로그인 → 현재 접속의 승인 요청 → Supabase 관리자의 해당 요청 한 건 승인 → 승인 결과 확인 순서로 진행합니다. 앱 설치는 브라우저의 설치/홈 화면 추가 기능을 이용합니다. 설치 자체로 접속이 승인되지는 않습니다.
4. 자료실의 「탈환 작전실 열기」 → 「서버 결과 새로 확인」을 누릅니다. 같은 응답의 확인 번호·요약·해시로 가린 operations_summary 서버 기록을 대조합니다. 메모 본문은 작전실에 표시하지 않습니다.
5. 「2단계 정상·금지 요청 실측」을 누르면 승인 세션과 비로그인 요청을 같은 목록 API로 보냅니다. 실제 HTTP 상태·응답 형식·요청 ID·UTC 시각을 한 표에 기록합니다. 정상 200과 비로그인 401을 각각 확인하고 CSV를 저장합니다. 불일치와 통신 오류도 그대로 남깁니다.
6. 나머지 단계는 표의 기대 결과에 따라 승인된 학습 환경에서 개별 확인합니다. 엔진 경유 여부·대상 커밋을 함께 남기고, 정상 허용과 금지 거부 모두 서버 기록과 맞는 범위만 완료로 기록합니다. 복원·회수 시험은 지정 대상과 사본을 먼저 확인합니다.

현재 PC에서는 저장소 밖의 `local-vault.mjs` 연결 도구로 http://localhost:8766/ 를 열고 있습니다. 이 도구는 로컬 화면을 기존 HTTPS 배포 API에 연결하며 저장소 설치물에는 포함되지 않습니다. 이 PC에서 다시 실행할 때는 해당 도구가 있는 폴더에서 `node local-vault.mjs`를 사용합니다. 새 PC에서는 위 Vercel 서버 구성 절차로 실행합니다. 정적 파일 서버만 실행하면 /api/*는 작동하지 않습니다.

### 재현 순서 4 — 중지

- 학생 판정·탐지 연습은 명령 종료 시 멈춥니다. 실행 중 중지는 해당 터미널의 Ctrl+C입니다.
- 접속 앱은 자료실의 로그아웃 결과를 확인한 뒤 창을 닫습니다. 서버 접근 회수가 필요하면 관리자가 지정 승인 한 건을 회수하고 후속 자료 요청 거부를 확인합니다.
- 로컬 연결 도구는 실행한 터미널에서 Ctrl+C로 중지합니다. 운영 자료실 서버의 중지는 Vercel 프로젝트 관리 절차를 따릅니다.
- ALEPH SDP 엔진의 기동·중지는 교육 운영 측에서 제공한 해당 버전의 절차로 수행합니다.

### 재현 순서 5 — 복구

1. git status와 git diff로 이번 변경과 다른 변경을 확인하고 복구 대상 파일·버전을 먼저 지정합니다. 현재 작업·비공개 사본·기존 감사 기록을 보존합니다.
2. 코드 복구는 확인한 정상 커밋의 지정 파일만 복원하고 새 커밋으로 기록합니다. 배포 복구는 확인한 정상 배포 버전으로 수행하며, DB 자료 복구 여부는 별도로 확인합니다.

4. B 메모 복원은 지정 사본·독립 기준 해시·승인된 B 세션을 확인한 뒤 POST /api/restore-note에 지정 id만 보내 수행합니다. 복원 후 ID·소유자·내용 해시와 대상 외 자료 보존을 확인합니다. 본문을 공개 기록에 넣지 않습니다.
5. 복구 후 학생 규칙 연습 → 실제 정상 요청 → 실제 금지 요청 순서로 다시 확인합니다. 새 커밋·요청 ID·확인 시각을 별도 행에 남깁니다. 이번 제작에서는 실제 복구를 실행하지 않았습니다.
